# Платформа для фотостудий — архитектура, версия 0.1

Черновик от 5 октября 2026. Основа: задача Алексея в проекте «Tomson Site»,
код сайта «Томсон» (репозиторий tomson-site), документы BroniOS, Event OS и
Light Plan на GitHub. Где написано «предположение» — я этого не проверял.

---

## 1. Что строим, одной фразой

«Студия под ключ»: владелец фотостудии за вечер получает сайт студии на
серверах Яндекса, кабинет, где сам меняет цены, фото и расписание, и готовые
связи с бронированием (BroniOS), Light Plan, Event OS, оплатой и соцсетями.
Платит подписку (решено Алексеем 05.10: проект коммерческий, платная подписка).

Отличие от конструкторов (Tilda, Vigbo, Taplink): конструктор даёт пустой лист
и кубики. Мы даём **готовую студию**: залы, цены за час, оборудование с
роликами, правила, сертификаты, фотошколу, бронь. Студии не нужно придумывать,
как устроен сайт, — только вписать своё.

«Томсон» — первая студия на платформе и образец. Перенос сайта «Томсон» (форма,
контакты, проверка с телефона, домены) идёт своим ходом и этим документом не
меняется.

## 1а. Два вида клиентов: фотостудии и фотошколы (Алексей, 05.10)

«мы делаем платформу для фотостудий и фотошкол, их можно использовать как
раздельно так и совместно».

- В ядре это два вида организации: **студия** (залы, оборудование, бронь) и
  **школа** (курсы, преподаватели, расписание занятий, афиша, работы учеников,
  запись и оплата учеников).
- Отдельно: студия без школы или школа без студии (школа может снимать залы у
  любой студии или заниматься онлайн) — свой сайт, свой кабинет, своя подписка.
- Вместе: как «Томсон» + фотошкола «Сфера» — две связанные организации у
  одного владельца, общий сайт или два сайта со ссылками друг на друга, занятие
  школы бронирует зал студии автоматически, общий кабинет с переключателем.
- Тариф — по модулям: «студия», «школа», «студия + школа».
- Фотошкола из п. 4.5 становится полноценным продуктом, а не модулем «потом».

## 2а. Event OS — ядро платформы (Алексей, 05.10)

**Алексей:** «EventOS … Это ядро платформы. У нас уже есть приложение
LightPlan, для него мы создали системы шв [ID] с привязкой к номеру телефона. Я
думаю мы сделаем что-то вроде быстрой системы авторизации на базе нашего
генератора ID».

Что это значит для устройства платформы:

```
                ЯДРО (Event OS, фаза Foundation)
   ID и учётные записи · организации и площадки · люди и роли
   права · уведомления · синхронизация · учёт подписок · API
        ▲            ▲              ▲              ▲
   Сайт студии    BroniOS       Light Plan     Event OS
   (этот проект)  (брони)       (фотограф)     (мероприятия)
```

- Сайт студии — **не отдельная система со своей базой людей**, а одно из
  приложений над ядром, как BroniOS и Light Plan. Студия в ядре — площадка с
  ID `pl<номер>`, её администратор и владелец — люди с ID `id<номер>`.
- Фаза Foundation из `90_Roadmap.md` Event OS (вход, организации, люди,
  проекты, права, уведомления, синхронизация) и этап «Ядро» этого документа —
  **одна и та же работа**. Делаем её один раз, в Яндекс Облаке, а не отдельно
  для сайта.
- «Головного сервера ID» (`BRIDGE_LIGHT_PLAN.md` §1, Light Plan `DECISIONS.md`
  3.09: «спрашивать не у кого») пока нет. Ядро и есть этот сервер: «такой ID
  существует, вот куда стучаться, вот его карточка».
- Не всё на сайте — «событие». Залы, цены, услуги живут у площадки
  (организации), не внутри Event; Event появляется, когда студия — исполнитель
  на мероприятии. Обычная бронь зала — топология 1 (`BRIDGE` §9): работает без
  Event OS-события, но на том же ядре (те же ID, права, уведомления).

### Вход по ID: как сделать быстро и не нарушить правило Event OS

В Event OS записано правило (`BRIDGE` §1, 3.09): **«ID адресует, аккаунт
удостоверяет. ID никогда не служит доказательством»** — потому что ID
вычисляется из номера, и любой, кто знает номер, знает ID. Значит, вход
«ввёл номер → вошёл» нельзя: войти мог бы кто угодно.

Быстрая авторизация, совместимая с этим правилом:
1. Человек вводит номер → ядро вычисляет `id<номер>` (как Light Plan).
2. Ядро присылает **одноразовый код** на этот номер и просит его ввести —
   это и есть доказательство, что номер в руках у человека.
3. Устройство получает долгий «пропуск» (сессию) и дальше не спрашивает.
4. Учётная запись заводится **лениво** (решение Event OS): только когда
   человеку надо держать данные — студии сразу, фотографу в Light Plan — когда
   понадобится.

Чем доставлять код — это деньги и надёжность, выбор на этапе «Ядро»:
- **SMS** — работает у всех, но платно за каждое сообщение;
- **звонок-сброс** (код — последние цифры номера звонящего) — обычно дешевле SMS;
- **Telegram / Max / VK** через бота — почти бесплатно, но не у всех есть;
- **VK ID / Яндекс ID** — вход «одной кнопкой», номер берётся оттуда
  подтверждённым.
Разумная схема по умолчанию: сначала мессенджер или VK ID, SMS — запасной путь.
Цены провайдеров не проверял.

Открытый вопрос из Event OS (`BRIDGE` §6): номер, переданный оператором
другому человеку. С кодом подтверждения новый владелец номера получит вход в
**чужую учётную запись**. Нужна защита: для владельца студии — второй способ
входа (почта) и уведомление при входе с нового устройства.

## 3. Из каких частей состоит платформа

```
              Посетитель студии            Владелец / администратор студии
                     │                                   │
          ┌──────────▼──────────┐             ┌──────────▼──────────┐
          │  САЙТ СТУДИИ        │             │  КАБИНЕТ СТУДИИ     │
          │  готовые страницы   │             │  (бывший /admin/)   │
          │  на своём домене    │             │  цены, фото, залы,  │
          └──────────┬──────────┘             │  заявки, статистика │
                     │ формы, бронь, оплата   └──────────┬──────────┘
                     └──────────────┬────────────────────┘
                          ┌─────────▼─────────┐
                          │  API ПЛАТФОРМЫ    │◄── Light Plan, Event OS,
                          │  (вход для всех)  │    BroniOS, чужие программы
                          └─────────┬─────────┘
       ┌──────────────┬─────────────┼──────────────┬───────────────┐
  ┌────▼────┐   ┌─────▼─────┐  ┌────▼─────┐  ┌─────▼──────┐  ┌─────▼──────┐
  │ База    │   │ Хранилище │  │ Сборщик  │  │ Уведомления│  │ Платежи    │
  │ данных  │   │ фото      │  │ страниц  │  │ почта, TG  │  │ ЮKassa и др│
  └─────────┘   └───────────┘  └──────────┘  └────────────┘  └────────────┘
                                     ▲
                          ┌──────────┴──────────┐
                          │ КАБИНЕТ ПЛАТФОРМЫ   │  ← Алексей: студии, тарифы,
                          │ (суперадмин)        │    оплаты подписок, поддержка
                          └─────────────────────┘
```

### 3.1. Сайт студии
- Готовые страницы (как сейчас): открываются мгновенно, поисковики их любят,
  сервер не нужен. Живое (форма, бронь, оплата) — маленькими окнами, которые
  обращаются к API.
- Адрес: бесплатный поддомен `studio.<платформа>.ru` сразу, свой домен студии —
  по желанию. Сертификат для https выпускается автоматически (сервис
  сертификатов Яндекса, Certificate Manager).
- Оформление — **темы**. Журнальный дизайн «Томсона» — тема №1. Студия выбирает
  тему и цвета, но не может «сломать» вёрстку: у каждого места на странице свой
  слот, как сейчас у фото.
- Страницы — **модули**, которые студия включает галочкой: залы, оборудование,
  правила и цены, как найти, сертификаты, расписание, фотошкола, фотосессии,
  доп. услуги, галереи, отзывы, новости.

### 3.2. Кабинет студии
- Вход через ядро: номер телефона → ID → одноразовый код (п. 2а), без паролей.
- **Три уровня администратора (Алексей, 05.10):** «владелец, администратор с
  полными правами чтения и изменения и модератор, читать отвечать, записывать,
  на всех уровнях права можно настраивать».

  | Уровень | По умолчанию | Чем отличается |
  |---|---|---|
  | Владелец | всё | единственный, кто управляет подпиской и оплатой, назначает и снимает людей, удаляет студию/школу; выдаёт и сужает права остальным |
  | Администратор | читает и меняет всё: цены, тексты, фото, залы, курсы, брони, заявки | без подписки и без управления владельцем |
  | Модератор | читает, отвечает на заявки и сообщения, записывает клиентов в бронь и учеников на курс | не меняет цены, тексты, настройки |

  Уровни — **готовые наборы галочек**, а не жёсткие роли: владелец может дать
  конкретному администратору «без цен» или модератору «может менять афишу».
  Права выдаются **на организацию** (студия или школа): один человек может быть
  администратором студии и модератором школы. Каждое действие пишется в журнал
  (кто, что, когда), владелец его видит.
  Толкование «записывать» = записывать клиентов на бронь и учеников на занятия —
  моё, уточнить у Алексея, если имелось в виду другое.
- Разделы: залы и цены, оборудование и ролики, фото, тексты, услуги,
  фотошкола, заявки, брони, статистика, настройки (домен, соцсети, оплата,
  счётчики), подписка.
- Каждое изменение сохраняет прошлую версию (как сейчас `_src/archive/`),
  «вернуть как было» — одной кнопкой.

### 3.3. Кабинет платформы (для Алексея)
Список студий, их тарифы и оплаты, кто сколько места занимает, вход в кабинет
студии «от её имени» для поддержки (с записью в журнал), рассылка студиям
о новых функциях.

### 3.3а. Подписки и биллинг (ядро, не модуль)
Раз платформа живёт на подписке, учёт оплат студий — часть ядра с первого
этапа «Ядро», а не дополнение в конце: тариф студии, дата следующего
списания, автосписание, счёт и закрывающие документы, что включено по тарифу
(модули, место под фото, сотрудники), пробный период, что происходит при
неоплате (напоминания → N дней работы → заглушка → хранение данных M месяцев).
Деньги студий за подписку и деньги клиентов студий (п. 4.10) — два разных
потока, они не смешиваются ни в базе, ни на счетах.

### 3.4. API платформы
API — это «служебный вход» для программ: вместо того чтобы человек открывал
страницу, другая программа спрашивает «какие залы у студии и сколько стоят» и
получает ответ в машинном виде.

- **Открытая часть** (без ключа, только чтение): карточка студии, залы, цены,
  оборудование, расписание свободных окон, афиша. Формат карточки — тот, что уже
  описан для Light Plan (`id, name, address, lat, lon, tel, hourMin, halls`).
- **Закрытая часть** (с ключом студии): создать заявку, бронь, запрос на
  продление, изменить цену.
- **Уведомления наружу** (вебхуки — платформа сама «стучится» в другую
  программу, когда что-то случилось): «новая бронь», «оплата прошла».
- Номер версии в адресе (`/v1/…`), чтобы старые программы не ломались при
  изменениях. Описание API — открытая страница документации.

### 3.5. Данные: где что лежит
- **База данных** — всё, что меняется и связано между собой: студии, люди и
  роли, залы, цены, услуги, заявки, брони, оплаты, статистика. Предложение:
  YDB в бессерверном режиме (Яндекс берёт деньги за запросы, при малой нагрузке —
  почти ноль) **или** управляемый PostgreSQL (привычнее разработчикам, но
  фиксированная плата каждый месяц). Это технический выбор — делаю его на шаге
  «Ядро» после расчёта стоимости, Алексею приношу итог.
- **Хранилище фото** — бакет, у каждой студии своя папка, лимит места по тарифу.
- **Сборщик страниц** — нынешний `render.mjs`, научившийся собирать сайт любой
  студии. Изменила студия цену → пересобрались только её страницы.
- **Разделение студий**: каждый запрос несёт «чья это студия», и база не отдаст
  чужое. Это главное требование безопасности платформы: одна студия никогда не
  видит заявки и клиентов другой.

## 4. Модули и связи

### 4.1. Бронирование — BroniOS
- Сейчас на сайте «Томсона» окно AppEvent; место под бронь на странице зала уже
  сделано заменяемым (решение 21.09).
- Для платформы бронь — модуль: студия выбирает «своя бронь (BroniOS)» или
  «внешняя система» (AppEvent, ссылка, телефон).
- BroniOS внутри платформы: календарь администратора остаётся тем же
  приложением, но данные броней живут в базе платформы в Яндексе, а Google
  Календарь — по желанию студии, как зеркало (без телефонов клиентов в нём).
- Канал Light Plan «продлить время», «позвать администратора» — идёт через API
  платформы, а не через отдельный Cloudflare Worker.
- Оплата брони: «вручную» (как в «Томсоне» сейчас, решение — эквайринг не
  добавлять) или предоплата онлайн — выбирает студия.

### 4.1а. Бронь как ссылка-переписка (по разбору AppEvent, 05.10)

Источник: разбор AppEvent, сделанный Алексеем в проекте BroniOS
(`APPEVENT_STATS_ANALYSIS.md`, на Mac; в этот открытый документ цифры выручки
и данные клиентов намеренно не перенесены).

**Позиция Алексея:** «мы делаем конкурента и нам не надо копировать, нам надо
превзойти их слабые места наша сила мой опыт и набитые шишки на их продукте
также в помощь».

**Решено Алексеем (из разбора, дословно там):** главный канал клиента —
страница брони по ссылке; почта и мессенджеры — «вторая линия обороны»;
клиент узнаёт об ответе сам по ссылке или по уведомлению браузера («Сообщать
мне»); SMS со ссылкой включает студия по желанию; автоотмена неоплаченного
времени есть, по умолчанию выключена, включает администратор.

**Ответы платформы на три открытых вопроса BroniOS** (предложение, не решено):

1. *Где хранить переписку, чеки и статусы.* В ядре платформы (п. 2а), в Яндекс
   Облаке: бронь, её переписка, статусы и файлы чеков — объекты ядра,
   привязанные к студии (`pl…`) и клиенту (`id…`). Противоречие с ROADMAP
   BroniOS («свой backend и база — не делаем сейчас») снимается так: BroniOS
   не строит свой сервер — он берёт хранение у ядра. Чеки — персональные и
   банковские данные: закрытое хранилище, доступ только студии и самому
   клиенту, срок хранения задаётся (например, 1 год после брони).
2. *«Простой бот».* По умолчанию — **автоответчик на самой странице брони**, без
   мессенджеров и без ИИ: подтверждение («время за вами»), как внести
   предоплату (QR, ссылка, перевод — что настроила студия), «администратор
   ответит в течение N минут» вне рабочего времени, напоминание об оплате,
   сигнал администратору, если клиент молчит. Тексты ответов настраивает
   студия, как шаблоны в AppEvent. Бот в мессенджере — позже, как вторая линия.
   Нужно подтверждение Алексея, что под «простым ботом» он имел в виду это.
3. *Как вернуть доступ к брони и не показать чужую.* Ссылка на бронь содержит
   **длинный случайный ключ**, а не номер телефона: угадать её нельзя. Тот же
   браузер помнит бронь сам. Ссылка потерялась → клиент на сайте вводит номер
   → получает **одноразовый код** на этот номер (тот же механизм, что вход по ID,
   п. 2а) → видит только свои брони. По одному номеру без кода — ничего. Плюс
   путь из цитаты Алексея: администратор сам присылает новую ссылку, старая
   перестаёт работать.

**Что из разбора берёт вся платформа, а не только BroniOS:**
- Статистика честная: «забронировано» и «оплачено» — разные цифры; прошлое
  отдельно от будущего; блокировка времени — не заказ и не клиент; дробные
  часы не округляются. Базовая аналитика (источники, UTM, цели Метрики) — в
  любом тарифе.
- Если канал уведомлений не работает (кончился баланс SMS, письмо отскочило) —
  тревога администратору, а не тишина.
- Клиент студии соглашается только с правилами студии, не платформы.
- Цены зала по числу людей, временные цены на даты, шаг 30 минут, минимум;
  один клик выбирает минимум зала сразу, с ценой.
- Источник заказа пишется сам (сайт, ВК, каталог, ссылка, администратор).
- **Импорт клиентской базы и истории из AppEvent** — обязательная часть мастера
  переезда: без истории студия не уйдёт.
- Ориентир цены: AppEvent 1 090 / 2 170 / 4 230 ₽ в месяц + SMS отдельно; в
  ROADMAP BroniOS есть идея оплаты за пришедшую бронь — вход в тарифы (п. 3.3а).
- Каталог студий как канал клиентов — у AppEvent есть (StudioGo); у нас — с
  оглядкой на правило Event OS «каталог — не маркетплейс».

### 4.2. Light Plan
Фотограф в Light Plan выбирает студию → приложение берёт её карточку из API
(залы, адрес, длина часа, азимут окон) и хранит снимок у себя, чтобы работать
без связи. Дальше — «продлить время», «вызвать администратора». Студия, которая
на платформе, появляется в Light Plan сама, без ручного ввода.

### 4.3. Event OS
Студия — исполнитель на мероприятии. Event OS берёт из API карточку студии и
отправляет запрос на бронь. Пока Event OS приостановлен — только место под
связь, ничего не строим. Правило Event OS «каталог — не маркетплейс» (без
комиссий и рейтингов) уважаем: если будет каталог студий, это решение Алексея
отдельно.

### 4.4. VK-сообщество → сайт
Как это видит владелец: вставляет ссылку на сообщество, разрешает доступ →
через минуту видит черновик сайта: название, описание, обложка, адрес,
телефон, ссылки, фото из альбомов, товары/услуги из раздела «Товары», посты
как новости → правит → «Опубликовать».

Что важно знать:
- Работает через официальный API ВКонтакте; нужно приложение VK платформы и
  согласие владельца сообщества. **Предположение** (не проверено): ВК отдаёт
  альбомы, товары и посты по такому доступу.
- Автоматически из ВК не понять, какой альбом — какой зал, и какие цены
  действуют. Поэтому результат — **черновик + мастер из 5 вопросов** (залы,
  цены за час, правила, адрес входа, бронь), а не готовый сайт без участия
  человека.
- Позже — двусторонняя связь: новость на сайте сама уходит в ВК и Telegram.

### 4.5. Доп. услуги, фотосессии, фотошкола
Общая сущность «услуга»: название, описание, фото, цена (из того же файла цен),
кнопка «записаться» (заявка или оплата). Фотошкола — услуги типа «курс» и
«мероприятие» с датами и афишей (как сейчас афиша «Сферы»: прошедшие остаются
видны). Фотосессия — услуга с фотографом и залом.

### 4.6. Галереи Wfolio (wfolio.ru)
Проверено 05.10 по сайту и документации (docs.wfolio.pro): Wfolio — чужой
сервис для фотографов: конструктор сайта + облачный диск для передачи снимков
клиентам, продажа фото, приём оплаты, печать фотокниг; есть партнёрство с
Яндекс 360. **Открытого API и встраивания клиентской галереи на чужой сайт в
документации нет** («Встроить» у них — свои альбомы внутри своего же сайта).
Галерея открывается по своей ссылке (можно свой домен, QR-код).

Значит, подключение — карточка галереи на сайте студии: обложка, название,
ссылка на Wfolio, загружает сама студия или фотограф. Автоматически тянуть
галереи нельзя, пока Wfolio не даст API (можно спросить их поддержку).

Wfolio ещё и **соседний конкурент**: он продаёт сайты фотографам, мы — студиям.
Пересечение — фотограф при студии и фотошкола.

### 4.7. Статистика
- Яндекс Метрика: у каждой студии свой счётчик, студия вписывает его номер в
  настройках (или платформа создаёт его сама — проверить, можно ли).
- Своя статистика в кабинете, на простых словах: сколько людей зашло, сколько
  нажали «позвонить», «написать в WhatsApp», «забронировать», сколько заявок,
  какая страница приводит клиентов. Это то, что владельцу студии важнее всего.
- Для Алексея: сводка по всем студиям (сколько активны, кто давно не заходил).

### 4.8. SEO (чтобы студию находили в Яндексе)
- Уже хорошо: готовые страницы, быстрая загрузка, свои адреса страниц.
- Добавить: карта сайта и правила для поисковиков (`sitemap.xml`,
  `robots.txt`), разметка «это фотостудия с адресом, часами и ценами»
  (schema.org — подсказки для поисковиков), заголовки и описания каждой
  страницы, красивые превью ссылок в мессенджерах (OpenGraph), подтверждение в
  Яндекс Вебмастере, карточка в Яндекс Бизнесе / Картах и 2ГИС, переадресация
  со старых адресов при переезде с другого конструктора.

### 4.9. Соцсети и мессенджеры
Кнопки WhatsApp, VK, Telegram, Max, Instagram (по решению 25.09 для «Томсона» —
все), лента ВК на сайте, автопостинг анонсов, Telegram-бот для администратора
(«новая заявка», «запрос на продление»).

### 4.10. Платежи — два разных денежных потока
1. **Клиенты студии платят студии** (предоплата брони, сертификат, курс).
   Деньги идут **напрямую на счёт студии**, через её собственный договор с
   ЮKassa, Т-Кассой или Робокассой (СБП, карты). Платформа только подключает её
   ключи. Так платформа не становится посредником в чужих деньгах (иначе —
   лицензии и банковский контроль). Обязательны онлайн-чеки (54-ФЗ) — у ЮKassa
   и Т-Кассы есть свои чеки.
2. **Студии платят платформе** (подписка). Автосписание раз в месяц (у ЮKassa
   это «автоплатежи»). Нужен договор платформы с платёжным сервисом — на
   юрлицо или ИП Алексея (п. 9).

## 5. Что, по-моему, упущено в задаче

Отсортировано по тому, насколько больно будет, если забыть.

1. **Персональные данные (152-ФЗ).** Сайт собирает имена и телефоны клиентов.
   Нужно: политика конфиденциальности и галочка согласия на каждой форме,
   уведомление Роскомнадзора об обработке данных, хранение данных россиян в
   России. Для платформы: студия — «оператор», платформа — «обработчик», между
   ними договор с поручением. Отсюда же: **BroniOS на Cloudflare и Google
   Календаре с телефонами клиентов для коммерческой платформы не годится** —
   переносим в Яндекс. Штрафы реальные, и это первое, о чём спросит любая
   серьёзная студия.
2. **Код платформы в открытом репозитории.** Все репозитории Алексея на GitHub
   публичные. Для коммерческого продукта это значит: любой конкурент копирует
   платформу целиком. Предлагаю закрытый репозиторий для платформы (п. 9).
3. **Юридическая обёртка продажи**: ИП/ООО, оферта для студий, тарифы, что
   будет с сайтом студии при неоплате (сайт работает ещё N дней, потом
   «заглушка», данные хранятся M месяцев).
4. **Выгрузка данных студии.** Студия должна уметь забрать свои тексты, фото,
   клиентов и уйти. Это вопрос доверия: без этого «на нас подсядут» звучит как
   угроза, и владельцы не придут.
5. **Мастер запуска и шаблон «пустой студии».** Обещание «очень быстро»
   держится не на сервере, а на том, что студия отвечает на 10 вопросов и
   получает сайт. VK-импорт — один из входов, второй — «заполнить с нуля»,
   третий — «перенести с Tilda/Vigbo» (вы это уже прошли руками с «Томсоном» —
   это готовая услуга).
6. **Отзывы.** Для студии отзывы на Яндекс Картах и 2ГИС часто решают больше,
   чем дизайн. Блок отзывов на сайте + просьба об отзыве после съёмки.
7. **Заявки как мини-CRM.** Форма → заявка в кабинете со статусом (новая, в
   работе, оплачена, отказ) + письмо/Telegram администратору. Сейчас в плане
   «Томсона» есть только письмо.
8. **Безопасность и надёжность**: блокировка после неверных входов, журнал
   действий, резервные копии базы, проверка доступности сайтов (если сайт
   студии упал — платформа узнаёт раньше студии).
9. **Поддержка**: справка с картинками, чат поддержки, страница «что нового».
10. **Стоимость студии для платформы.** Нужен расчёт: сколько стоит одна
    студия в месяц в Яндекс Облаке (хранилище, запросы, база, почта, домен).
    Без этого не назначить тариф. Цифры не считал — это отдельный короткий шаг.
11. **Лимиты по тарифу**: место под фото, число залов, модулей, сотрудников.
12. **Доступность и телефон**: 80% посетителей студий — с телефона. Правило
    «375 px без горизонтальной прокрутки» из проекта «Томсон» — для всех тем.
13. **Конкуренты** — не изучал. Стоит отдельным шагом посмотреть, что
    предлагают студиям AppEvent, Vigbo, Wfolio, «Студиобукинг»-подобные сервисы
    (названия не проверены), чтобы понять, чем мы лучше и что берут за деньги.

## 6а. Где платформа живёт в Яндекс Облаке
Сейчас (скриншот Алексея 05.10): облако `novopashinlab`, по каталогу на проект —
alicesoulledger, bronios, camerachange, camerateka, eventos, lightplan, rascad,
suncompass, tomson. Предложение:
- **новый каталог `platform`** — база, API, кабинеты, сборщик, сайты всех студий;
  создаётся на этапе «Ядро» с согласия Алексея (платные ресурсы);
- **не каталог на студию**: студии разделяются внутри базы и хранилища, иначе
  сотня студий = сотня каталогов и ручных настроек;
- `tomson` остаётся как есть до переноса «Томсона» на платформу, потом
  освобождается;
- `bronios` — до решения на этапе «Ядро», остаётся ли бронь отдельным сервисом
  со своим API или переезжает в `platform`;
- со временем — отдельное облако или платёжный аккаунт под юрлицо платформы,
  чтобы счета Яндекса за платформу не смешивались с личными проектами.

**Алексей 05.10:** «пока идет разработка будет на моем аккаунте, но на данном
сервере по сути расположены все проекты объединенные на одной платформе».
Значит: облако `novopashinlab` — общий дом всех проектов (BroniOS, Light Plan,
Event OS, сайт студий и др.), разработка на аккаунте Алексея; перенос на
юрлицо — отдельной строкой дорожной карты.

Предложение (не решено): раз проекты живут на одной платформе, общие вещи
делать один раз — вход (одна учётная запись студии/фотографа для BroniOS,
кабинета сайта, Light Plan), учёт подписок, API-шлюз. Решать по мере того,
как второй проект реально к этому подключится, не заранее.

## 7. Главные технические правила платформы

1. Страницы сайта — готовые файлы; живое — только там, где без него нельзя.
2. Цена — одна переменная (как сейчас).
3. Данные клиентов — только в России, только в базе платформы.
4. Одна студия никогда не видит данные другой; проверяется автоматическим тестом.
5. Любое изменение в кабинете можно откатить.
6. Секреты (ключи оплаты студий, пароли почты) — только в хранилище секретов
   Яндекса (Lockbox), никогда в репозитории и в чате.
7. API с номером версии; старые программы не ломаются.
8. Сервисы и связи (BroniOS, Light Plan, Event OS, Wfolio, ВК, платежи) — через
   API, а не прямым доступом к чужим данным.
